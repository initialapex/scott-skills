# NXP with the MCUXpresso SDK (LPC, Kinetis, i.MX RT, MCX)

Contents: how the layers map · SDK structure and the config tools · the driver pattern
the SDK already uses · a port: I2C · a port: UART with the transfer handle · interrupts and
priorities · i.MX RT memory and cache · RTOS · build and tools · testing · pitfalls

Scope: MCUXpresso SDK (`fsl_*` drivers) in C for LPC5500/LPC800, Kinetis, i.MX RT, and MCX
families, built with MCUXpresso IDE, the VS Code extension, CMake, or Keil/IAR project
files from the SDK builder. SDK generations differ (the older SDK 2.x packages from the
SDK Builder versus the newer Git-based `mcuxsdk` with west/CMake): confirm the layout and
names in the SDK version of the project. Driver function names below are those of the
common `fsl_*` drivers; the exact set varies per device family.

## How the layers map

| Layer | Where |
|-------|-------|
| SDK (not yours) | `drivers/` (`fsl_lpuart.c`, `fsl_lpi2c.c`, ...), `CMSIS/`, `device/` (startup, `system_*.c`), `components/`, `middleware/` (USB, lwIP, FreeRTOS, ...) |
| generated by the config tools | `board/pin_mux.[ch]`, `board/clock_config.[ch]`, `board/peripherals.[ch]`, board files `board.[ch]` |
| app, service, driver, hal, common | your own folders; no `fsl_*.h` |
| port | `ports/nxp/port_nxp_*.c`: the only files including `fsl_*.h` and `board.h` |
| board | `board/board_<name>.c`: instances, pin and bus choices (built on the generated init) |

## SDK structure and the config tools

- The **Pins**, **Clocks**, and **Peripherals** tools of MCUXpresso Config Tools generate
  `BOARD_InitBootPins()`, `BOARD_InitBootClocks()`, and `BOARD_InitBootPeripherals()`
  (plus `BOARD_InitDebugConsole()`). Regenerate them from the `.mex` file, do not hand-edit
  them, and call them from `main()` before your `board_init()`:

```c
int main(void)
{
    BOARD_InitBootPins();
    BOARD_InitBootClocks();
    BOARD_InitBootPeripherals();       /* only if the Peripherals tool is used */
    board_init();                      /* yours: builds the objects, returns fw_status_t */
    app_start();                       /* never returns, or runs the loop / starts the RTOS */
}
```

- **Version-control the `.mex`** with the generated files; a changed pin or clock is
  reviewed as a diff of both.
- Clock frequencies come from `CLOCK_GetFreq(...)`; pass them into port configs instead of
  hard-coding (`LPUART_Init` and `LPI2C_MasterInit` take the source clock in Hz).

## The driver pattern the SDK already uses

`fsl_*` drivers are consistent, which makes ports predictable:

1. a **config struct** with defaults from `XXX_GetDefaultConfig(&cfg)`;
2. `XXX_Init(base, &cfg, srcClock_Hz)` / `XXX_Deinit(base)`;
3. **blocking** calls (`LPUART_WriteBlocking`, `LPI2C_MasterTransferBlocking`);
4. **non-blocking transactional** calls with a **handle**: `XXX_TransferCreateHandle(base,
   &handle, callback, userData)`, then `XXX_TransferSendNonBlocking(...)`; the callback
   signature includes `userData`, **which maps straight to our `void *ctx`**;
5. return type **`status_t`** (`kStatus_Success` = 0, `kStatus_Fail`, `kStatus_Timeout`,
   `kStatus_InvalidArgument`, `kStatus_Busy`, plus driver-specific codes such as
   `kStatus_LPI2C_Nak`).

So a port holds `base` (the peripheral register block, e.g. `LPUART1`), a handle when the
transactional API is used, and the object's lock.

## A port: I2C

```c
/* port_nxp_lpi2c.c */
#include "fsl_lpi2c.h"
#include "hal_i2c.h"

typedef struct port_nxp_i2c {
    hal_i2c_t base_if;               /* first member (named so it does not clash with `base`) */
    LPI2C_Type *base;                /* e.g. LPI2C1 */
    osal_mutex_t lock;
} port_nxp_i2c_t;

static fw_status_t map_status(status_t s)
{
    if (s == kStatus_Success)          { return FW_OK; }
    if (s == kStatus_Timeout)          { return FW_ERR_TIMEOUT; }
    if (s == kStatus_InvalidArgument)  { return FW_ERR_INVALID_ARG; }
    if (s == kStatus_LPI2C_Busy)       { return FW_ERR_BUSY; }
    return FW_ERR_IO;                  /* kStatus_LPI2C_Nak, arbitration lost, FIFO error, ... */
}

static fw_status_t port_write_read(hal_i2c_t *iface, uint8_t addr7, const uint8_t *tx, size_t tx_len,
                                   uint8_t *rx, size_t rx_len, uint32_t timeout_ms)
{
    port_nxp_i2c_t *self = FW_CONTAINER_OF(iface, port_nxp_i2c_t, base_if);
    lpi2c_master_transfer_t xfer = {0};
    status_t s;
    fw_status_t st;

    if (osal_mutex_lock(&self->lock, timeout_ms) != FW_OK) { return FW_ERR_BUSY; }

    xfer.flags = kLPI2C_TransferDefaultFlag;
    xfer.slaveAddress = addr7;                   /* 7-bit, unshifted: the driver adds the R/W bit */
    xfer.direction = kLPI2C_Read;
    xfer.subaddress = (tx_len == 1u) ? tx[0] : fw_get_be16(tx);   /* up to 4 bytes, big-endian */
    xfer.subaddressSize = tx_len;
    xfer.data = rx;
    xfer.dataSize = rx_len;
    s = LPI2C_MasterTransferBlocking(self->base, &xfer);

    st = map_status(s);
    osal_mutex_unlock(&self->lock);
    return st;
}
```

`LPI2C_MasterTransferBlocking()` has no timeout parameter in many SDK versions, so a stuck
bus can block forever; enable the peripheral's pin-low timeout (`pinLowTimeout_ns`
in the master config) and, where it must be bounded, use the non-blocking transfer with a
semaphore wait that honors `timeout_ms`. State this in the port and test the stuck-bus
case on target. (Check the `lpi2c_master_transfer_t` field names for the SDK version; the
sketch limits `tx_len` to what `subaddress` can carry.)

## A port: UART with the transfer handle

```c
typedef struct port_nxp_uart {
    hal_uart_t base_if;
    LPUART_Type *base;
    lpuart_handle_t handle;
    ring_buffer_t rx;                         /* filled from the ISR/callback */
    uint8_t rx_byte;                          /* one-byte receive re-armed by the callback */
    hal_uart_rx_cb_t on_rx; void *on_rx_ctx;
} port_nxp_uart_t;

/* Matches lpuart_transfer_callback_t; userData is our object (ISR context). */
static void uart_cb(LPUART_Type *base, lpuart_handle_t *handle, status_t status, void *userData)
{
    port_nxp_uart_t *self = (port_nxp_uart_t *)userData;
    FW_UNUSED(base); FW_UNUSED(handle);

    if (status == kStatus_LPUART_RxIdle) {
        (void)ring_buffer_write(&self->rx, &self->rx_byte, 1u);
        arm_rx(self);                         /* LPUART_TransferReceiveNonBlocking(...) again */
        if (self->on_rx != NULL) { self->on_rx(self->on_rx_ctx); }
    }
}

/* init: LPUART_GetDefaultConfig(&cfg); cfg.baudRate_Bps = ...; LPUART_Init(base, &cfg, clk_hz);
 * LPUART_TransferCreateHandle(base, &self->handle, uart_cb, self); arm_rx(self); */
```

For continuous reception at higher baud rates, the SDK offers ring-buffer receive
(`LPUART_TransferStartRingBuffer`) and DMA/eDMA handles; the same port shape applies.
Status names (`kStatus_LPUART_RxIdle`) are driver-specific: confirm in the header.

## Interrupts and priorities

- IRQ handlers have fixed vector names from the startup file (`LPUART1_IRQHandler`); the SDK
  driver provides them or expects you to call the driver's handler
  (`LPUART_TransferHandleIRQ(base, &handle)`); the `fsl_*` drivers include IRQ glue that calls
  your registered callback. Keep your code in the callback, and the port as the only file that
  registers it.
- Enable with `EnableIRQ(IRQn)`; set priority with `NVIC_SetPriority(IRQn, p)`. Many SDK
  handlers end with `SDK_ISR_EXIT_BARRIER` (a `DSB` that prevents re-entry from a stale
  pending flag on fast cores); keep it when writing your own handlers on M4/M7.
- With FreeRTOS, ISRs that call `...FromISR` must be at or below the
  `configMAX_SYSCALL_INTERRUPT_PRIORITY` level; Cortex-M NVIC on these parts has 3 or 4
  implemented priority bits depending on the family
  ([interrupts-concurrency.md](interrupts-concurrency.md)).

## i.MX RT memory, cache, and XIP

i.MX RT parts execute from external QSPI/OSPI flash (XIP) through FlexSPI, and have tightly
coupled memories and a cache, so placement decides behavior:

- **Code and data regions**: ITCM (code, fastest), DTCM (data, fastest, **not DMA-visible on
  most parts**), OCRAM (DMA-capable, cached), and external SDRAM. The SDK provides
  attributes that the linker script honors: `AT_QUICKACCESS_SECTION_CODE(func)` and
  `AT_QUICKACCESS_SECTION_DATA(var)` for ITCM/DTCM, `AT_NONCACHEABLE_SECTION(var)` and
  `AT_NONCACHEABLE_SECTION_ALIGN(var, align)` for DMA buffers that should skip the cache,
  `SDK_ALIGN(var, 32)` for cache-line alignment.
- **Cache coherence**: if the DMA buffer is in cacheable OCRAM, clean/invalidate with
  `DCACHE_CleanByRange()` / `DCACHE_InvalidateByRange()` (or the CMSIS `SCB_*DCache_by_Addr`)
  around transfers, with 32-byte alignment; otherwise put it in a non-cacheable section.
- **Interrupt latency from XIP**: an ISR running from flash can take a cache miss; put
  time-critical handlers and their data in ITCM/DTCM (`AT_QUICKACCESS_SECTION_CODE`).
  Ops tables read from such a handler are `const` data in flash: place them in a RAM section
  too if the latency matters.
- Never reconfigure the FlexSPI or flash while executing from it; flash writes are done
  from RAM with interrupts managed (use the SDK's `flexspi_nor` examples as the
  reference).
- The **boot header** (IVT, boot data, FCB) and image layout are part of the board files
  and the linker script; do not move them.

## RTOS

FreeRTOS ships in the SDK `middleware` with a project-specific `FreeRTOSConfig.h`. Use the
same `osal_freertos.c` as other FreeRTOS ports. The SDK's `fsl_*` drivers are not
thread-safe by default: the port's lock around the **whole** transaction is what makes a
bus shareable, and its use inside the driver callback (ISR context) must not take the
lock.

## Build and tools

- MCUXpresso IDE, the VS Code extension, CMake projects from the SDK builder, and the newer
  west-based `mcuxsdk` all compile the same sources; keep your folders buildable from
  any of them with plain include paths and a flat source list.
- Debug through CMSIS-DAP/J-Link/LPC-Link2; the semihost/console choice
  (`BOARD_InitDebugConsole`, `PRINTF`) should be compiled out of production firmware.
- Flash programming (LinkServer, J-Link, `blhost` for secure/bootloader flows) writes the
  device, and secure-boot or fuse settings (OTP, HAB/AHAB on i.MX RT) cannot be
  undone: show the command and let the developer run it.

## Testing

Host tests of drivers and services use the template approach
([testing-host.md](testing-host.md)); no `fsl_*` header is included in them. On target,
loopback tests (two UARTs wired together, a GPIO loop, an EEPROM on I2C) check each port; the
stuck-bus and timeout cases are the ones to prove.

## Pitfalls

- Passing the 8-bit address (shifted) to an SDK API that adds the R/W bit itself, or the
  reverse; read the driver header.
- Blocking transfers without a timeout on a bus that can hang.
- DMA buffer in DTCM, in cacheable memory without maintenance, or with a size that is
  not a multiple of the cache line.
- Editing the generated `pin_mux.c`, `clock_config.c`, `peripherals.c` by hand (the next
  regeneration drops the change).
- Calling the driver's blocking API inside a callback (ISR context).
- Clock gates and the pin mux set in one tool and assumed in another (a peripheral works
  in the debugger session and not after a power cycle because the debugger left a clock on).
- Mixing SDK versions across the `drivers/` and `device/` folders after an SDK update.
